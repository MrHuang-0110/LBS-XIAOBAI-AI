# 小白-Ai MCU ↔ ASRPRO UART 交互协议 v0.9

- 更新日期：2026-09-28（v0.9：等待词条的主动唤醒。MCU→ASRPRO 新增 `wakeup=<sec>` /
  `sleep` 两条帧，供编程模式"等待词条"期间由主控主动唤醒语音芯片、识别到后立即退出唤醒。
  帧格式、ID 表、其它帧全部不变）
- 物理层：UART 9600 8N1 全双工
- 目标 MCU：PY32F030K28U6TR
- 语音芯片：ASRPRO
- 最大帧长：**32 字节**（含帧尾）

---

## 一、帧格式

ASCII 文本。两个方向都用 **`=`** 作为 tag 与数值的分隔符，且**都带帧尾**。

**MCU → ASRPRO：** 帧尾 `\n`（LF 0x0A）

```
<tag>[=<dec>]\n
```

**ASRPRO → MCU：** 帧尾 `\r\n`（CR 0x0D + LF 0x0A）

```
<tag>[=<dec>]\r\n
```

- `tag`：全小写英文字母，长度 ≤ 8（例如 `play` / `cmd` / `wake` / `sleep` / `done` / `stop` / `ping` / `wakeup`）
- `dec`：十进制数值字符串（1..3 位，`1`、`01`、`10`、`100` 均接受，值 ≤ 255）
- 收方在遇到帧尾（MCU→ASR 的 `\n` 或 ASR→MCU 的 `\r\n`）时判定为一个完整帧

**为什么两方向都带帧尾？**

- v0.6 起两方向统一带帧尾。语音端图形化工具（天问/ASRPRO）用 `serial_readstr` 按行读取，依赖帧尾 `\n` 做**确定性分帧**——无帧尾时它只能靠字符间静默超时断帧，会导致粘包（如 `play=17play=27`）和额外延迟。加帧尾后这些问题被根治。
- MCU 端接收用 UART DMA + IDLE 中断，兼容有无帧尾（收到 `\r\n` 或 `\n` 均正确剥尾）。

**其它约束：**

- 单帧超 32 字节 → 收方丢弃
- 未识别 tag、格式非法、数值 > 255 → 收方静默忽略
- 命令 ID 范围 1-16 与 42-51，播报 ID 范围 17-41 与 52-63，互不重叠
- `sleep` 在两个方向都出现且同义（MCU→ASR 是"请你去睡"，ASR→MCU 是"我已经睡了"）；
  `wakeup`（请求）与 `wake`（事件）刻意不同名，避免抓包时混淆

## 二、命令表

### MCU → ASRPRO（发送时带 `\n` 尾）

| 帧文本 | 语义 | 说明 |
| ---------------- | ------------ | --------------------------- |
| `play=<id>` | 播报预置语音 | id = 播报 ID（17-41 / 52-63，见第三节） |
| `stop` | 停止当前播报 | — |
| `ping` | 心跳/存活探测 | — |
| `wakeup=<sec>` | 主动进入唤醒 | v0.9 新增；`sec` = 唤醒窗口秒数（1-255），到点未续期则由语音端自行休眠。用于编程模式"等待词条" |
| `sleep` | 立即退出唤醒 | v0.9 新增；请求语音端马上回到唤醒词模型并上报 `sleep\r\n`；已休眠时为幂等空操作 |

> ⚠️ **`sleep` 与 `wakeup` 必须串行**：语音端的"退出唤醒"是**异步**流程，且会**先把退出
> 口播播完**才切回唤醒词模型（实测退出口播 0.61s 静音版 / 2.45s"我去休息"版）；而"进入
> 唤醒"只在状态已是未唤醒时才切命令词模型。若在退出还没落定时就发 `wakeup`，语音端只会
> 重装定时器、不切命令词模型，随后落定的退出又把模型切回唤醒词组 → 下一个等待词条永远
> 识别不到（连续两个"等待词条"积木卡死的根因）。**主控做法：① 词条命中后延迟约 400ms
> 再发 `sleep`，期间若又来了"等待词条"就取消（连续等待全程不发 sleep，芯片保持唤醒）；
> ② 已发 `sleep` 时必须等语音端上报 `sleep\r\n` 再发 `wakeup`，兜底超时 3000ms。**

### ASRPRO → MCU（发送时带 `\r\n`）

| 帧文本 | 语义 | 说明 |
| ------------------- | ------------ | --------------------------- |
| `cmd=<id>\r\n` | 语音命令识别 | id = 命令 ID（1-16 / 42-51，见第四节） |
| `wake\r\n` | 检测到唤醒词 | 对应识别 ID=0，独立成帧不带数值 |
| `sleep\r\n` | 进入休眠 | v0.8 新增；`sys_sleep_hook()` 上报，主控熄灭呼吸灯 |
| `done=<id>\r\n` | 播报完成 | id = 上次播报的 ID（17-41 / 52-63） |

## 五、示例

**MCU 请求播开机语：** 发送 8 字节 `play=17\n`（hex: `70 6C 61 79 3D 31 37 0A`）

**MCU 请求播"进入编程模式"：** 发送 8 字节 `play=52\n`（hex: `70 6C 61 79 3D 35 32 0A`）

**ASRPRO 识别到"前进"：** 发送 7 字节 `cmd=6\r\n`（hex: `63 6D 64 3D 36 0D 0A`）

**ASRPRO 上报编程模式词条：** 发送 8 字节 `cmd=42\r\n`（hex: `63 6D 64 3D 34 32 0D 0A`）

**ASRPRO 上报开机语播报完成：** 发送 9 字节 `done=17\r\n`

**ASRPRO 检测到唤醒词：** 发送 6 字节 `wake\r\n`

**ASRPRO 进入休眠：** 发送 7 字节 `sleep\r\n`

**MCU 打断当前播报：** 发送 5 字节 `stop\n`

**MCU 请求主动唤醒（编程模式进入"等待词条"，窗口 30s）：** 发送 10 字节 `wakeup=30\n`
（hex: `77 61 6B 65 75 70 3D 33 30 0A`）

**MCU 请求立即退出唤醒（词条命中/程序取消）：** 发送 6 字节 `sleep\n`（hex: `73 6C 65 65 70 0A`）

## 六、变更记录

- **v0.9 (2026-09-28)**：等待词条的主动唤醒。MCU→ASRPRO 新增 `wakeup=<sec>`（主动进入
  唤醒，窗口秒数）与 `sleep`（立即退出唤醒）；语音端分别映射到 SDK 的
  `enter_wakeup(sec*1000)` 与 `exit_wakeup_deal(0)`。ID 表、帧格式、其余帧不变。
- **v0.8 (2026-09-16)**：编程模式词条。命令段新增 42-51（ASR_01–ASR_10），播报段新增
  52（进入编程模式）、53（退出编程模式）、54-63（P01–P10）；新增 `sleep` 事件；
  词条 2/4/19/21 去掉"进入"。帧格式与 v0.7 相同。
- **v0.7 (2026-07-23)**：ID 表按实际录制资源重排。命令 ID 改为 1-16 连续（唤醒词=0），播报 ID 改为 17-41 连续，两段不重叠。协议帧格式无变化，只是数值范围调整。
- **v0.6 (2026-07-09)**：MCU→ASR 新增帧尾 `\n`；两方向统一带帧尾。语音侧改按行确定性分帧，MCU 侧删除播报后 500ms 阻塞延时。根治"播报丢失/不同步/传输慢"。
- **v0.5 (2026-07-03)**：两方向统一 `=` 分隔（去掉 v0.3/v0.4 的 `:`）；MCU→ASR 保持无帧尾（IDLE 分帧），ASR→MCU 带 `\r\n`。
- **v0.4 (2026-07-03)**：取消所有帧尾；MCU→ASR 用 `=`，ASR→MCU 用 `:`。
- **v0.3 (2026-07-03)**：不对称分隔符 `=` / `:`；数值统一 dec；带 `\r\n`。
- **v0.2 (2026-07-03)**：ASCII 文本、冒号分隔、hex 数值。已废弃。
- **v0.1 (2026-07-03)**：定长 6 字节二进制帧。已废弃。
